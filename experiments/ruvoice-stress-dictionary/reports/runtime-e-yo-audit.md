# Статический аудит runtime-путей е/ё

**Дата:** 2026-11-25  
**Ветка:** `stress-dictionary-pipeline`  
**Базовый HEAD:** `ff48904eddbb2c62922deb7e70a3997660b239d4`  
**Статус:** частичный аудит; словарные ключи проверены, морфологический индекс имеет незакрытый риск.

## Что проверено

Проверены центральные runtime-пути чтения и применения словарей: `DictCache`, `Dicts`, `DictLines`, `Layers`, `Stress`, `StressCorrectionMerger`, `Replacements`, `YoDict` и `StressBin`, а также генератор `tools/aot_morph.py`.

### Русские ключи словарей ударений сохраняют е/ё

- `RuLayer.dictWord()` использует базовую реализацию без преобразования букв.
- `DictCache.stress()` строит карту из точного `lowercase()` ключа; `Dicts.key()` для удаления системной строки тоже сохраняет различие е/ё.
- `StressCorrectionMerger` сводит е/ё только для выравнивания слов между результатами моделей. Для защиты пользовательских ключей и составных слов используется отдельный `normalizeExactKey()`, который е/ё не объединяет.
- Фильтрация системных замен по пользовательским словам в `DictCache` также сравнивает точные lowercase-токены.
- Регрессионные тесты уже проверяют, что пользовательский ключ `берёг` не защищает `берег`, а точный ключ `берег` защищает именно его.

### Найденные преобразования с ограниченной областью действия

- `Replacements.keepCase()` допускает е/ё-эквивалентность только при переносе регистра и ударного маркера в замену, не при поиске ключа.
- В `Stress` преобразование е/ё в `fuseKa()` и `vseYo()` используется для специальных грамматических условий.
- `StressBin.yoEntries()` намеренно переводит входной ключ safe-словаря «ё» к варианту с «е»: это отдельный словарь восстановления орфографии, а не основной словарь ударений.
- Диагностическое сравнение и выравнивание независимой модели также допускают е/ё-эквивалентность, но не меняют идентичность пользовательской словарной записи.

## Незакрытый риск: AOT morph.bin

В `text/Morph.kt` функция `Morph.hash()` приводит `ё` к `е` перед FNV-хешированием. Генератор `tools/aot_morph.py` делает то же самое при формировании ключей. Кроме того:

- генератор включает POS `N`, `A`, `ORD_NUM` и `PA`; глагольный POS не включён;
- формы объединяются операцией `table[form] |= t` уже после сведения `ё` к `е`;
- runtime-таблица хранит только 64-битный хеш и битовую маску, а исходное написание формы не сохраняет.

Следствие: разные написания, различающиеся только е/ё, неразличимы для `Morph.tags()`. Например, форма существительного `берег` и глагольная форма `берёг` попадают в один нормализованный ключ; поскольку глагольные формы отфильтрованы генератором, запрос по явному `берёг` потенциально получает именные морфологические теги от `берег`. Это не коллизия 64-битного хеша, а преднамеренное сведение орфографии на этапе нормализации.

Это не доказывает, что каждая такая пара уже приводит к неверному ударению, но означает, что морфологические эвристики могут получить неверный POS/набор грамматических признаков даже при явно написанной `ё`. Поэтому аудит runtime е/ё нельзя считать завершённым.

## Почему исправление не внесено в этом коммите

В ветке отсутствуют исходные `morphs.json` и `gramtab.json`; в Git хранится только готовый `morph.bin` размером около 13,3 МБ. Переход на точный хеш без повторной генерации потеряет морфологические данные для форм, у которых AOT хранит вариант с «ё» или без неё. Переписывать бинарный ассет вручную либо маскировать проблему точечным списком исключений небезопасно.

Правильное продолжение требует исходного AOT-корпуса и новой схемы индекса: точное написание должно иметь приоритет для явно введённой «ё», а fallback для текста без «ё» должен сохранять неоднозначность; формы исключённых POS должны препятствовать заимствованию тегов от другой лексемы с тем же е/ё-ключом.

## Границы результата

- Это аудит ключевых runtime-файлов, а не заявление о полном аудите всех 78 production-файлов.
- `Системный.txt`, другие production-словари, APK assets и `main` не менялись.
- Полный dump ru.wiktionary не скачан: прямая загрузка из текущей среды завершилась DNS-ошибкой. Extractor прошёл unit-тесты, но статистики полного corpus run нет.
- Десять gold-кандидатов всё ещё ожидают независимой второй лингвистической разметки; 16 форм семейства `четырёхбедрум…` остаются заблокированными до человеческой проверки произношения.

## Следующие действия

1. Получить исходные AOT `morphs.json` и `gramtab.json` той же версии, из которой построен текущий `morph.bin`.
2. Спроектировать новую версию morph-индекса с точными surface-формами и безопасным fallback для написания без «ё».
3. Добавить тесты как минимум на `берег/берёг`, `все/всё` и на формы с «ё», чьи теги должны сохраниться.
4. Не переносить этот runtime-риск в production-словарь и не считать точность gold-набора измеренной, пока не завершены независимые разметки.
